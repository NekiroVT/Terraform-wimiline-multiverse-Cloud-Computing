02 / operación

Cómo se conectan los servicios

Aplicación · AWS

Usuarios → ALB → EC2

El balanceador recibe HTTPS y distribuye tráfico a instancias privadas en dos zonas. Auto Scaling mantiene 2 instancias y permite crecer hasta 4.

Datos · AWS

API → PostgreSQL

La API se conecta a RDS PostgreSQL Multi-AZ por TCP 5432. La base es privada y dispone de copias automáticas con siete días de retención.

Continuidad · Azure

S3 → EC2 → Blob

Las EC2 envían el respaldo y la versión de aplicación a Blob por HTTPS con SAS limitada. El firewall permite solo las IP NAT autorizadas; la VM Azure usa Private Endpoint.

03 / evidencia

Qué se comprobó

Recuperación entre nubes

La base y el paquete vinculado se recuperaron desde Azure y superaron SHA-256; la aplicación aislada respondió en 4 min 28 s por HTTP restringido. En otra prueba, HTTPS con certificado válido y resolución local forzada funcionó en 5 min 39 s. El certificado se emitió antes y el DNS productivo no cambió.

Alta disponibilidad y escalamiento

La sustitución controlada de una EC2 mantuvo 75 de 75 respuestas HTTP 200. Una carga sintética elevó la capacidad deseada de 2 a 4 instancias; no equivale a una prueba de capacidad máxima de usuarios.

Monitoreo y correo

CloudWatch y SNS supervisan AWS; la alarma de CPU RDS recibe datos. Azure Monitor recibió syslog y una alerta temporal se activó; el responsable confirmó el correo. También se confirmó el correo de bienvenida real de la aplicación.

Restricciones y decisiones

AWS Academy limitó operaciones de S3, actualización gradual de instancias, IAM y precios. Se emplearon Terraform con apoyo de AWS CLI y el flujo de respaldo aprobado. Azure bloqueó la prueba directa del grupo de acciones; una regla temporal permitió comprobar la notificación.

Operación: las metas de RTO y RPO son objetivos. La SAS de carga a Azure vence el 19/12/2026 a las 19:00, hora de Lima. El presupuesto alerta, pero no detiene los cargos.
